# История трансформаций

Единое хранилище и просмотр истории всех трансформаций — и файлов, и
изображений, — плюс сохранение результатов и их скачивание.

## Устройство

```
transformation.ts        вид, статус, разрешение RBAC
entities/                таблица transformations
history-access.ts        кому чью историю можно — одно определение на всё
history-write.service    запись строки и сохранение файла
history-read.service     чтение: права, фильтры, курсор
history-download.service выдача сохранённого файла
history-retention        уборка просроченных записей вместе с файлами
history.controller       своя история и свои файлы
admin/                   то же по указанному пользователю
```

Сами файлы лежат не здесь: за них отвечает `src/storage/`, а этот модуль
знает только про `FileStorage` — общее понятие.

Одна таблица, а не две, потому что этого требует ТЗ — и потому, что иначе
не собрать страницу: курсор означает «продолжи с этого места» в одном
упорядоченном наборе, а из двух независимых таблиц такого места нет.

Направление зависимостей одностороннее: модули конвертации получают
`HistoryWriteService` и пишут в него, а этот модуль о них ничего не знает.
Единственное исключение — словари форматов для фильтра (см. ниже), и там
импортируются перечисления, файлы без зависимостей, так что кольца не
возникает.

## Что изменилось в модулях конвертации

Своих таблиц у них больше нет. `file_conversions` заменена на
`transformations`, а трансформация изображений, которая раньше писала
только в журнал приложения, теперь попадает в общую историю. Запись у
обоих идёт через один сервис, поэтому «единое хранилище» держится
устройством, а не договорённостью: писать больше некуда.

## API

`GET /api/transformations/history` — своя история. Прав не требует и
номера пользователя не принимает: чью историю отдавать, решает токен.
`?userId=` в таком окне рано или поздно забывают проверить.

`GET /admin/users/{userId}/transformations/history` — история указанного
пользователя. Требует право `transformations@history_admin`; свою историю
можно смотреть и без него.

`GET /api/transformations/history/{itemId}/download` — скачать свой
сохранённый результат.

`GET /admin/users/{userId}/transformations/history/{itemId}/download` — то
же по указанному пользователю, по тому же праву.

Коды списка: `200`, `400` (параметры, курсор, номер пользователя), `401`,
`403`, `404` (только у административного окна), `429`.

Коды скачивания: `200`, `400` (номер не UUID), `401`, `403` (чужая
запись или нет права), `404` (записи нет, файл не сохраняли или он пропал
из хранилища), `410` (срок истёк), `429`.

Порядок проверок в административном окне — сначала право, потом
существование пользователя. Наоборот было бы удобнее для отладки, но по
разнице между `404` и `403` посторонний перебирал бы номера,
выясняя, какие аккаунты существуют.

### Параметры

| Параметр | Значение |
| --- | --- |
| `cursor` | курсор следующей страницы, из `nextCursor` предыдущего ответа |
| `limit` | 1–100, по умолчанию 20 |
| `type` | `file` или `image` |
| `sourceFormat`, `targetFormat` | `csv`, `json`, `xml`, `yaml`, `png`, `jpeg`, `svg`, `unknown` |
| `status` | `success` или `error` |
| `createdAtFrom`, `createdAtTo` | границы периода, включительные |

Список форматов не написан руками, а собран из перечислений обоих модулей
конвертации: новый формат станет фильтруемым сам. `unknown` — записи, у
которых формат определить не удалось; по ним видно, что кто-то
систематически шлёт не то.

Незнакомый параметр — отказ `400`, а не тишина: опечатка в `staus` иначе
просто не отфильтровала бы ничего, и человек решил бы, что записей нет. По
той же причине перевёрнутый период (`from` позже `to`) — тоже отказ, а не
пустой список.

Период принимает дату (`2025-01-31`, это полночь UTC) и момент со
смещением (`2025-01-31T12:00:00Z`). Время **без** смещения не принимается:
`2025-01-31T12:00:00` в разных часовых поясах означает разные моменты, и
угадывать за клиента — верный способ отдать не тот период.

### Ответ

```json
{
  "items": [
    {
      "id": "…",
      "type": "image",
      "sourceFormat": "svg",
      "targetFormat": "png",
      "status": "error",
      "fileSize": 4096,
      "durationMs": 12,
      "errorCode": "400",
      "createdAt": "2025-06-01T12:00:00.000Z",
      "saved": false,
      "expiresAt": null
    }
  ],
  "nextCursor": "eyJ2YWx1ZSI6…"
}
```

`errorCode` есть только у отказов и равен коду ответа, которым
закончилась попытка. Отдельного словаря символьных кодов в приложении нет,
а заводить его ради одного поля значило бы завести вторую систему
обозначений рядом с уже понятной.

Имени исходного файла в ответе нет: в контракте оно не заявлено, а через
административное окно видны чужие записи. В таблице имя лежит — для
разбора происшествий.

`nextCursor` равен `null` на последней странице. Курсор непрозрачен: это
деталь реализации, а не часть контракта.

`saved` означает не «сохраняли ли», а «можно ли скачать прямо сейчас»: у
записи с истёкшим сроком файла уже нет, и показывать по ней кнопку
скачивания значило бы обещать лишнее. Ключ файла в ответе не появляется
никогда — см. ниже.

## Сохранение результата

`POST /api/convert` и `POST /api/images/convert` принимают поле
`save=true` (по умолчанию `false`). Результат ложится в хранилище, а в
строке истории появляются ключ файла и срок его жизни.

Сохранение идёт **до** ответа, а не в фоне. ТЗ в одном месте просит не
блокировать выдачу файла, а в другом — отвечать `500` на сбой хранилища;
второе выполнимо только синхронно: у ответа, который уже ушёл, кода не
поменять. Отдать файл и молча его не сохранить — значит соврать: человек
увидел бы в истории запись без обещанного файла. На диске запись занимает
миллисекунды.

Порядок внутри — файл, потом строка. Строка с ключом несуществующего файла
обещает то, чего нет; файл без строки — просто мусор на диске. Из двух
рассогласований выбрано то, которого пользователь не видит, а если строка
всё-таки не записалась, файл убирается следом.

Результат крупнее `TRANSFORMATION_MAX_SAVE_BYTES` — отказ `413` с
предложением повторить без `save`. Лимит проверяется до записи: смысл
лимита в том, чтобы не занять диск, и «сначала запишем, потом проверим»
этот смысл теряет.

## Скачивание

Скачивание идёт **по номеру записи истории**, а не по ссылке на файл, и
это главное решение здесь. Ключ в хранилище наружу не отдаётся никогда:
ссылка на файл, даже неугадываемая, — это доступ без проверки, который
нельзя отозвать и нельзя привязать к человеку. По номеру записи право
проверяется на каждый запрос, и отозванное право перестаёт работать сразу.

Отсюда же защита от IDOR: подставить свой `userId` к чужой записи не
поможет — в административном окне запись ищется сразу вместе с владельцем,
и чужая для него неотличима от несуществующей.

Три разных «нет файла» означают разное: сохранения не просили — `404`
(файла и не было); срок истёк — `410` (ТЗ разрешает и `404`, но `410`
честнее: видно, что ссылка не сломана, а устарела); в хранилище пусто —
`404` плюс запись в журнал, потому что так выглядит рассинхронизация базы
и диска.

Тело отдаётся потоком: файл на сотню мегабайт не оседает в памяти целиком.

## Пагинация

Курсорная, а не по номеру страницы. На `OFFSET` база отсчитывает
пропускаемые строки каждый раз заново, и десятая страница стоит дороже
первой; плюс между запросами человек продолжает конвертировать — и строки
съезжают, повторяясь или пропадая. Ответ на одни и те же параметры
стабилен, как требует п. 1.6 ТЗ.

Курсор — пара (время, id). Один только момент не годится: две конвертации
в одну миллисекунду разъехались бы между страницами. Кодирование общее со
списком пользователей — `common/cursor.ts`.

Порядок один и не настраивается: новые сверху. Истории вопрос «что было
недавно» задают почти всегда, а каждый дополнительный порядок — это ещё
один индекс и ещё одна форма курсора.

## Настройки

| Переменная | По умолчанию | Что задаёт |
| --- | --- | --- |
| `TRANSFORMATION_HISTORY_RETENTION_DAYS` | 90 | сколько дней хранить историю; `0` — не удалять |
| `TRANSFORMATION_HISTORY_CLEANUP_HOURS` | 24 | как часто убирать просроченное |
| `TRANSFORMATION_MAX_SAVE_BYTES` | 32 МиБ | потолок размера сохраняемого результата |
| `UPLOAD_DIR` | `./assets` | где лежат файлы (подпапка `transformations/`) |

Уборка своя, без планировщика: тянуть `@nestjs/schedule` ради одной задачи
раз в сутки незачем. Первый проход — сразу при старте (приложение могло
простоять неделю), дальше по таймеру; таймер помечен `unref`, иначе
процесс не завершался бы по `SIGTERM`.

Убирает она и строки, и файлы, порциями по 500: ходить в хранилище за
каждым файлом не бесплатно, а выбрать миллион строк разом — значит надолго
занять и память, и диск. Порядок тот же, что при сохранении: сначала файл,
потом строка. Если файл убрать не удалось, строка **остаётся** — удалить
её значило бы навсегда потерять след файла, и с диска его уже никто не
уберёт; на следующем заходе она всё ещё просрочена и попробует снова.

Срок жизни файла (`expiresAt`) хранится в строке, а не вычисляется из
`createdAt` при каждом запросе: срок в настройках могут поменять, и уже
сохранённые файлы не должны менять свою судьбу задним числом.

## Право администратора

ТЗ называет право `transformations.history.admin`; в этом проекте права
записываются как «ресурс@действие», поэтому то же самое выглядит как
`transformations@history_admin`.

Право должно существовать в таблице `permissions` — иначе `RbacService`
отказывает всем, включая администратора: неизвестное разрешение он
трактует как запрет, и правильно делает. Создаёт его `npm run seed`
вместе с назначениями (admin — всё, support — просмотр чужой истории,
чтобы разбирать обращения «у меня не конвертируется»). На готовой базе то
же самое делается через `/admin/rbac/*`.

## Безопасность и аудит

- Своё окно не принимает номер пользователя вовсе; чужое — проверяет право
  до всего остального.
- В журнал пишутся актор, чья история, параметры запроса, код ответа и
  число строк. Значения фильтров писать можно — это форматы и статусы, —
  а содержимого файлов в истории нет вообще.
- Проверка права живёт в сервисе, а не в наклейке `@RequirePermission`:
  так отказ попадает в журнал вместе с тем, чью историю пытались открыть.
  Наклейка знает только имя права.
- Внешнего ключа на `users` у таблицы нет: история переживает удаление
  аккаунта, как и журналы auth и rbac. Её срок жизни определяет срок
  хранения, а не удаление пользователя.
- Файлы приватны: прямых ссылок нет, доступ только через проверку права на
  запись истории. Правило доступа — одно на список и на скачивание
  (`history-access.ts`): размноженное по сервисам, оно однажды разъедется
  молча, и тестом «список не пускает» дыру в скачивании не поймать.
